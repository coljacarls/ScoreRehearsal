# ScoreRehearsal – Developer notes

How ScoreRehearsal is built on top of MuseScore Studio, how to build it, and how releases and
MuseScore updates work. For what the app does, see the [README](../README.md).

## Repository layout

```
build.cmd                 Windows build script (MSVC + Ninja + Qt 6)
build-web.sh              build script of the web version (Qt for WebAssembly, PWA)
src/
  appshell/               the application shell: window, rehearsal page, commands (C++ / QML)
  cmake/Configure.cmake   which MuseScore modules are built, branding
  cmake/App.cmake         executable name, icon, app resources
  app/app.qrc.in          app resources (themes, shortcuts) taken from the MuseScore tree
  branding/               icon (generated by make_icon.py), no MuseScore assets
  web/                    web version: page, loader, service worker, manifest, tools, tests
musescore/                git submodule: fork of MuseScore Studio, branch "rehearsal-app"
  muse/                   git submodule: fork of the Muse framework
```

The MuseScore submodule is the real build root. MuseScore knows several *build configurations*
(`app`, `app-portable`, `app-web`, ...); the fork adds **`app-external`**, which builds a shell
that lives outside the MuseScore tree. `build.cmd` configures MuseScore with

```
-DMUSESCORE_BUILD_CONFIGURATION=app-external -DMUE_EXTERNAL_APP_DIR=<this repo>/src
```

and MuseScore then includes `src/cmake/Configure.cmake`, adds `src/appshell` in place of its own
`appshell` module and links everything into `ScoreRehearsal.exe`. Nothing of ScoreRehearsal is
compiled into MuseScore Studio itself.

### What the fork branch contains

The branch `rehearsal-app` of the MuseScore fork differs from upstream only in:

- the rehearsal view core (session-only mix and solo state in `PlaybackController`,
  `RehearsalTracksPanel`, tap-to-seek and `viewModeOverride` in the notation view), plus the
  "Rehearse" tab of the full MuseScore app;
- the generic `app-external` hooks: a block in `SetupConfigure.cmake`, one `elseif` in
  `src/CMakeLists.txt`, a few lines in `src/app/CMakeLists.txt`, `src/app/app_config.h.in` and
  `src/app/main.cpp`;
- `MUE_BUILD_APPJS_MODULE`: builds the `appjs` web module (JS API, audio start, sound font) for an
  external app on WebAssembly without switching to the `app-web` configuration (4 small hooks in
  `src/CMakeLists.txt`, `src/app/CMakeLists.txt`, `app_config.h.in`, `appfactory.cpp`);
- a two-line ASIO build fix in the Muse framework submodule.

## Building (Windows)

Requirements: Visual Studio 2022 Build Tools (C++ toolchain, CMake and Ninja components),
Qt 6.11 for MSVC 2022 (default location `C:\Qt\6.11.2\msvc2022_64`, override with the
`QT_DIR` environment variable), Python 3 (MuseScore build scripts), git.

```
git clone --recurse-submodules https://github.com/coljacarls/ScoreRehearsal.git
cd ScoreRehearsal
build.cmd install Release
build\Release\install\bin\ScoreRehearsal.exe path\to\score.mscz
```

`build.cmd configure|build|install|run|clean [Release|Debug|RelWithDebInfo]`; the install step
runs `windeployqt`, so `build\<type>\install` is a complete, relocatable application directory.

The app version comes from the `SCOREREHEARSAL_VERSION` environment variable (set by CI) or,
for local builds, from `git describe --tags` (`0.0.0-dev` without tags). It is shown on the
start screen and in the About dialog.

## Building (web)

The web version is the same app compiled with Qt for WebAssembly (single thread) plus a PWA
shell in `src/web`. Plan, decisions and status: [pwa-plan.md](pwa-plan.md).

Requirements (Linux or WSL): Qt 6.11 for WebAssembly (`wasm_singlethread`) and Qt 6.11 for the
build machine (`QT_HOST_PATH`), the Emscripten SDK version that Qt requires (4.0.7 for Qt 6.11,
activated with `source emsdk_env.sh`), CMake, Ninja, Node 22.

```
export QT_WASM_DIR=$HOME/Qt/6.11.2/wasm_singlethread QT_HOST_PATH=$HOME/Qt/6.11.2/gcc_64
./build-web.sh all        # build/web/app, build/web/audio, then dist/web
./build-web.sh serve      # http://localhost:8080/ (localhost counts as secure: service worker works)
```

`build-web.sh build` compiles two things: the app (`MUSESCORE_BUILD_CONFIGURATION=app-external`, with
`OS_IS_WASM` the block at the end of the switches in `src/cmake/Configure.cmake` applies) and the
audio engine (`musescore/src/web/audioengine`, runs in an AudioWorklet). `package` puts them
together with `src/web` (`src/web/tools/package.mjs`) and writes the service worker with the list of
all files; `dist/web` can be served by any static web server, e.g. GitHub Pages.

Tests of the page, loader, service worker, offline start, update flow and the presentation tab
need no Qt (they run against a fake build in Chromium):

```
cd src/web && npm install && npx playwright install chromium && npm test
```

How the web version differs from the desktop version:

- **Files.** The browser has no paths. A score that is picked (or launched, or shared to the
  installed app) is written to memory (`/interactive`), and `web::libraryPath()` copies it to the
  score library `/files/data/library/<content hash>/` so that its session finds it again.
  `/files/data` is an IndexedDB file system (`src/web/storage.js`); it also holds `sessions.json`
  and the settings. The page writes it back after changes (`web::persistStorage()`) and asks the
  browser not to delete it (`navigator.storage.persist()`). The original file is never written.
- **Sound.** Browsers allow sound only after a tap: the page shows a start button when the app and
  the audio driver are ready.
- **Presentation.** A second browser tab (`?mode=presentation`) instead of a window. The rehearsal
  tab sends it the score once and then the state (position, part, solo, laser pointer, settings)
  as JSON through a `BroadcastChannel` (`src/web/presentation.js`, `WebBridge`,
  `RehearsalPage.qml`, `PresentationPage.qml`). The tab plays nothing and never writes the storage.
- **Updates.** A new version waits in the background until the user taps "Update".
- **Hosting.** GitHub Pages cannot send COOP/COEP headers, so there are no threads yet
  (`MUSE_THREADS_SUPPORT OFF`).

## Releases

`.github/workflows/release.yml` builds and publishes a GitHub release (zip of the install
directory, tag `vX.Y.Z` on the merge commit) when a pull request is merged into `main` and
either its title contains a version (`Release v1.0.1`) or it has a label `release:major`,
`release:minor` or `release:patch` (bumps the latest tag). Other pull requests do not release.

The pull request description becomes the release notes on the GitHub release page, followed by
the notes GitHub generates. Describe the new features, improvements and fixes there, written for
users.

## Updating the MuseScore dependency

MuseScore is pulled in through the submodule, so updating is a merge in the fork plus a pointer
update here:

```
cd musescore
git fetch upstream
git merge upstream/master                # resolve conflicts in the few patched files, if any
git push origin rehearsal-app
cd muse                                   # only if upstream moved the muse submodule
git fetch upstream && git merge upstream/main && git push origin rehearsal-app
cd ../..
build.cmd install Release                 # rebuild and smoke-test
git add musescore && git commit -m "Update MuseScore to <date>"
```

After a merge, check that the web version still builds (`./build-web.sh all`) and compare
`src/cmake/Configure.cmake` with the `APP-WEB` block in
`musescore/SetupConfigure.cmake` and the option lists in `musescore/CMakeLists.txt` and
`musescore/muse/framework/cmake/MuseDeclareOptions.cmake`: new module options should be switched
off explicitly unless the app needs them.

## Behaviour

- Starts in the dark theme (switchable in the `…` menu); the choice is remembered.
- Scores open in the continuous (horizontal) view; page view is available from the view button.
- Scores are never saved: no autosave, no "save changes?" prompt, no migration dialog for files
  from older MuseScore versions (they are shown as saved).
- No network access: no update checks, no cloud, no MuseSounds / Muse Hub.

## Keyboard shortcuts

MuseScore's default shortcuts apply where the commands exist: `Space` play/pause, `Ctrl+O` open,
`F11` full screen, `Ctrl+Q` quit. Closing a score is in the `…` menu.
